These RESEARCH Assumptions are carried INTO the plan but are surfaced for operator confirmation, not silently baked in. The executor implements them as written; if the operator overrides, the override is a config-driven change (the values are config-derived, not hardcoded in logic).

- **A1 (SRCH-04, security-sensitive) — the vetted engine subset.** Proposed `keep_only`: `duckduckgo`, `brave`, `wikipedia`, `wikidata`. Rationale: ≤4 upstream hosts, all high-trust general/reference engines; excludes Google/Bing direct (rate-limit/CAPTCHA self-hosted), social/forum engines (injection surface), and image/video engines (out of scope for v1.5 text grounding). This is the auditable outbound surface Phase 33's `villa verify search` will cross-check — keep it minimal. The list is rendered from a single source so a future operator change is a one-line edit + golden re-freeze.
- **A4 — the secret_key route.** Generate the secret ONCE via `crypto/rand` at first opt-in, persist in `config.toml` (0600 via existing `SaveVilla`), render READS it from config (so the golden uses a fixed test secret), and it is injected into the container via `$SEARXNG_SECRET` — NEVER rendered into the 0644 settings.yml or unit. Never `math/rand`; never logged.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config.toml (operator-editable, 0600) → render | Hand-edited config is untrusted input; render must fail closed, never widen a bind |
| render output (0644 unit + settings files) → local users | Unit/settings files are world-readable by design (systemd --user reads them); secrets must not land here |
| villa-searxng container → upstream search engines | The ONLY sanctioned outbound from this service; bounded by the engine allowlist |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-01 | Information Disclosure | engine set in settings.yml (SRCH-04) | mitigate (blocking-high) | Render `use_default_settings.engines.keep_only` to the vetted ≤4-host subset (duckduckgo/brave/wikipedia/wikidata) from a single-source slice — NEVER the full ~80-engine default. The rendered allowlist is the auditable outbound surface (golden-frozen). Tied to SC#3 acceptance. |
| T-29-02 | Information Disclosure | secret_key (V3/V6) | mitigate (blocking-high) | Generate via `crypto/rand` (never `math/rand`), persist in config.toml (0600), render reads it and injects via `$SEARXNG_SECRET` env; the settings.yml template renders `secret_key` empty so the secret NEVER lands in a 0644 file. Never logged. Tied to SC#2 acceptance. |
| T-29-03 | Tampering | searxng image literal | mitigate | Digest-pin the resolved amd64 manifest from the official ghcr.io/searxng org (rolling tag is not pinnable); literal lives only behind the `SearXNGImage()` seam, allowlisted in TestSeamGrepGate in the same commit. |
| T-29-04 | Elevation / scope creep | render bind | mitigate (blocking-high) | No host port / no publish line in the .container template; container-DNS reachability only on villa.network. normalizeVilla never widens SearxngAddr to a routable bind (PRIV-01). Accidentally publishing a host port would expose the service to every local process — prevented by construction (no publish directive exists). Tied to SC#1 acceptance. |
| T-29-05 | Tampering / privacy | off-render drift | mitigate | WebSearchEnabled-gated append-only branch; the 13 existing goldens stay byte-identical with web search off (SC#4 / PRIV-07), proven by a negative golden test. |
