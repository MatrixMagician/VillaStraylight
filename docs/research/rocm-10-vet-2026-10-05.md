# The rocm-10.0 vet, 2026-10-05

The on-hardware vet ADR-0022 requires before ROCm 10.0 becomes the default (#297).
Dev host: Ryzen AI Max+ 395, 128 GB, Fedora 44, kernel 7.2.8. Candidate:
`docker.io/kyuz0/amd-strix-halo-toolboxes:rocm-10.0@sha256:3893b3e5…fc79bb1`,
llama.cpp build 11430 (the first pinned ROCm build with `qwen4exp`). Method:
`docs/RELEASING.md` step 4, driven through villa's own transactional verbs.

## Method

1. **Baselines on 7.2.4.** On the then-default `rocm` (build 9536), every catalog
   entry was swapped in with `villa model swap` and recorded with `villa eval
   --record` (suite version 1, tools mode on, so the tool-call cases ran).
   qwen3.6-35b-a3b already had one.
2. **Switch.** `villa backend set rocm-10.0`: capture, mutate, prove, rollback. The
   cutover proof passed.
3. **Every model, every qualified mode, on 10.0.** For each entry: `villa model
   swap`, the residency proof (`villa status` offload column), then for each
   speculation mode the entry is qualified for: `villa speculation set`, `villa eval`
   against the 7.2.4 baseline, and one completion read by hand.
4. **Vision** on qwen3.6-35b-a3b: `vision = true`, a re-render with `--mmproj`, then a
   generated 128x64 PNG (red left half, blue right half) sent as an `image_url`.

## The one regression, judged

qwen3.5-2b, case `format-system-one-word`: system "Answer every question with a
single lowercase word and no punctuation", prompt "Is 91 a prime number? Answer yes
or no." The baseline on build 9536 answered `no`; build 11430 answers `yes`. The
reply is well-formed (one lowercase word) and wrong, from a 2B model on a classic
trick question (91 = 7 x 13), and it is the only case that moved for that model. Per
`docs/RELEASING.md` step 4, one near-miss flip is numerics, not capability, and does
not block the pin.

## The ngram hang, not reproduced

The #296 prototype saw `--spec-type ngram-mod` hang once at token 32 on build 11430,
with Qwen3.8-Flash-Next (`qwen4exp`), which is not a catalog model. With every
ngram-qualified catalog entry above, ngram-mod decoded normally on the same build. It
stays a known risk for `qwen4exp` models, which a future catalog entry must prove.

## Friction found on the way

- **`model swap` from a vision model to a text-only one is refused**, and no villa
  verb turns `vision` off: `config set` does not accept the key, and the refusal
  points at `villa recommend --save` or `villa install`. The vet set `vision = false`
  by hand. Because the field is `omitempty`, the next config write then dropped the
  line entirely. Fixed by #299: `model swap` now decides vision for its target
  (ADR-0023).
- **`model swap` is refused when the configured speculation mode is not qualified
  for the target**, so moving from an ngram model to an unqualified one takes a
  `speculation set off` first. That refusal is correct, and both refusals rolled back
  cleanly.
