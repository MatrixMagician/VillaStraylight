# v1.8 spec — `villa update`

The transactional check → fetch → prove → prune lifecycle for the stack's pinned
components. Assembled from the closed tickets on
[the v1.8 map](https://github.com/MatrixMagician/VillaStraylight/issues/83); every
claim here traces to the ticket that decided it.

> **Status: implemented.** Every piece §7 listed is written and gated. The one
> thing outstanding is not code: the ed25519 signing keypair has not been generated,
> because that must happen on a machine that is neither this one nor CI. Until it
> is, `manifestverify.publicKeyHex` is empty and villa can verify nothing — so every
> manifest is refused and every host falls back to its compiled-in pins. That is the
> correct behaviour for the unset state, and deliberately not "skip the check".
> See [§9 Open items for a human](#9-open-items-for-a-human).

## 1. The problem

Every component the stack runs is pinned by digest, and **every pin is a
compile-time constant**. "A newer version exists" has no representation anywhere in
the tree. There is no verb to move a pin, no record of what a host is actually
running versus what villa shipped, and no way to learn that an upstream image was
rebuilt.

This is not theoretical. Measured on 2026-08-26
([research](../research/update-version-checks.md)), **eight of ten pins had already
drifted**, with Crush fifteen minor versions behind. `vulkan-radv` was rebuilt
hours before the measurement.

## 2. The shape of the answer

```
villa update --check                  read-only; works on a stopped stack
villa update --check --from-registries   opt-in, per-component, fingerprints the host
villa update --dry-run                the ordered plan and download total
villa update                          apply to every updatable subsystem
villa update <subsystem>...           apply to named subsystems
villa update --json                   machine shape for --check
```

Arguments are **subsystems** — `inference`, `chat`, `memory`, `search`, `agent` —
never container names, because the proof unit is the verify verb's scope
([#89](https://github.com/MatrixMagician/VillaStraylight/issues/89)).

Exit codes reuse `doctor`'s vocabulary rather than inventing one: `0` current /
all proven, `2` updates available / updated-with-a-WARN, `1` could-not-check /
proof failed / refused, `130` interrupted.

Full transcripts for every state: [`prototype/villa-update-cli.md`](../prototype/villa-update-cli.md).

## 3. The core model

### 3.1 A pin is two values

The single decision the rest hangs on
([#86](https://github.com/MatrixMagician/VillaStraylight/issues/86)).

| | **Vetted pin** | **Effective pin** |
|---|---|---|
| Means | "villa's maintainer proved this on gfx1151 hardware" | "this host is running this" |
| Lives in | the compiled-in `pins.Table` | the `pinstate` store |
| Mutable | no | yes, only after a proven update |
| Absent/corrupt | a build-time programming error (panic, as `loadCrushPolicy` does) | an expected runtime condition (fail closed to the vetted pin) |

They are equal on a fresh install and diverge only when an update commits. This is
what lets `doctor` say *"running a digest villa never vetted"*, gives rollback a
target, and lets a fresh install start from a known-good table with zero network
trust.

### 3.2 The working set is the installed footprint

Not the pin table ([#84](https://github.com/MatrixMagician/VillaStraylight/issues/84)).
`update` operates on what this host actually runs, resolved from config plus what
Podman reports present — symmetric with `doctor`/`status`, and honest, since
[#89](https://github.com/MatrixMagician/VillaStraylight/issues/89) can only prove
what is installed.

**In scope:** the *active* backend image, Open WebUI, Qdrant + embedder (memory
on), SearXNG + websafe (search on), the Crush binary (agent on), and villa itself
(reported only).

**Skipped, with the reason stated:** disabled addons, and the three non-active
backend images. Skipping the latter is not tidiness — proving a non-active backend
would require swapping to it, so four backends would mean four swaps and four
residency proofs in one run. It also keeps the **vulkan landing spot known-good**:
it is the rollback target precisely because it is proven, and freshening it
unproven would degrade the thing rollback depends on.

**Out of scope:** all model weights, including the embedding GGUF. That one is a
named exception rather than an oversight — `nomicEmbedShard` has no `model
pull`/`swap` verb over it, but advancing it silently invalidates every vector in
Qdrant, which is **embedding skew** as `CONTEXT.md` defines it. `update` may
advance the embedder *image*, never the *weight*: the image is a runtime, the
weight is an identity.

### 3.3 Pins come in three shapes

Not one, and no single check mechanism covers all three
([#85](https://github.com/MatrixMagician/VillaStraylight/issues/85)).

| Shape | Components | A moved digest means |
|---|---|---|
| `rolling_digest` | Open WebUI `:main`, SearXNG, distroless | a new upstream build — expected, no version to name |
| `version_tag` | ROCm, vulkan-radv, Qdrant | **the same declared version was rebuilt** — not a version bump |
| `checksummed_asset` | Crush | a genuine new release |

The middle row is why `--check` must not flatten "rebuilt" and "new version" into
one word. `rocm-7.2.4` moving digest means **the image villa validated on hardware
is no longer the image that tag names**, while nothing about "ROCm 7.2.4" changed.

**Automated version selection is not viable and must not be attempted.** The
backend repo carries 1478 tags, 97% dated build variants; the list is not
version-ordered (Qdrant's ends on `v1.9.x`, *older* than the pinned `v1.18.2`, so
taking the tail is a downgrade); it contains an ambiguous `rocm-7.14` and an
upstream misspelling `vulkan-radv-perfromance`. Choosing a version is
irreducibly curatorial.

## 4. Where new pins come from

### 4.1 A signed manifest, with the binary as the fallback

New vetted pins arrive in an **ed25519-signed manifest** published as a GitHub
release asset. The signing key is offline and never touches CI; the public key is
compiled into the binary, so manifest trust is anchored exactly where every other
pin's trust already lives.

This sets the right ceiling: **the manifest is no more trusted than the binary**,
and a compromised binary is already game over.

`crypto/ed25519` is standard library, so this costs **no new dependency**.
Sigstore/cosign was rejected for v1.8 — stronger, but it costs a Go dependency
plus Rekor/Fulcio trust roots and extra outbound, and under a curated model the
human curator is the trust anchor.

**The compiled-in table is always the fallback.** Fetch fails, signature fails,
manifest expired, or host offline ⇒ vetted pins. No network, no problem.

### 4.2 The manifest supplies values only

The compiled-in table is a **hard allowlist**, not just a default.

- **Allowed:** a new digest for a component the table names; a new version tag; new
  floors; new Crush checksums.
- **Refused:** a component the table does not name; a registry host not already
  present; any change to a URL template.

A manifest carrying components and URL templates would be a remote-code-execution
channel with extra steps. Under this rule a stolen key can move you to a bad
*version of a component you already run* — bounded, and the prove step still has to
pass — but cannot make villa fetch from a host you never trusted.

**Consequence:** adding a component to the stack always requires a new villa
release. That is correct — introducing a new executable is exactly the decision
that should require shipping a binary you signed.

### 4.3 Freshness: a signature proves authorship, not currency

Three attacks survive signature verification using a manifest villa genuinely
signed: **replay/downgrade**, **freeze**, and **rollback-after-fix**.

1. **A monotonic serial.** Villa refuses a manifest whose serial is below the
   last-seen serial. Loud refusal, not silent acceptance.
2. **A signed `valid_until`.** Past it, the manifest is treated as **absent** and
   villa falls back to compiled-in pins. Freezing degrades to fail-closed.
3. **`CheckedAt` recorded**, so `status`/`doctor` can say *"last checked 200 days
   ago"* rather than implying currency.

**Two places where `jsonstore`'s absent-means-empty reading must NOT be applied
naively**, because in both the zero value is the unsafe direction:

- the **serial floor** — an absent store must fall back to the compiled-in vetted
  serial, never zero, or deleting the store resets the downgrade floor;
- the **reference set** for pruning — an absent store must mean *retain
  everything*, never "nothing is referenced, delete freely" (ADR-0004).

### 4.4 Floors travel with the pin

`internal/preflight/rocm-policy.json` is compiled in exactly like the image pins.
A newer ROCm image can demand a newer kernel or Mesa than the shipped floors
encode, and **a registry cannot report the floor a digest needs** — a floor is a
claim about what was tested on hardware, which `update` cannot re-derive over the
network.

So floors are an attribute of the ROCm pin, and `update` **re-runs the existing
preflight gate against the new pin's floors before mutating anything**. A BLOCK
refuses with remediation rather than pulling an image the host cannot run.

## 5. The apply lifecycle

### 5.1 Per subsystem, sequenced, halting on the first failure

Not one transaction. Each subsystem is proven and **committed before the next
begins**, so a failure reverts only that subsystem. The vetted/effective split
makes a mixed state representable and legible rather than a lurking
inconsistency; `doctor` reports partial-update state explicitly.

Order: **inference → chat → memory → search → agent.**

### 5.2 The sequence for one subsystem

```
prove current  →  capture  →  mutate  →  prove new  →  commit  →  prune
                     │                        │
                     └── rollback ────────────┘
```

**Proving the current state first** is what the swaps never needed: a swap
presupposes a running stack, so it mutates something demonstrably working.
`update` has no such guarantee. Without the pre-check, villa could mutate an
already-broken subsystem, fail, roll back, and report *"the update failed"* when it
was broken beforehand. A pre-existing failure is therefore a **refusal**, not an
update failure.

**The proof unit is the verify verb's scope**, so Qdrant + embedder move together
(one `verify memory`), as do SearXNG + websafe (one `verify search`). Splitting
them would produce pairings with no proof and no meaning.

| Subsystem | Proof |
|---|---|
| inference | residency proof (ADR-0001, two signals) + a real generation probe |
| chat | `internal/openwebui` protocol probes |
| memory | `verify memory` |
| search | `verify search` |
| agent | `verify agent` |

### 5.3 Reject rolls back, unchanged

`residency.Cutover`'s existing rule is inherited without softening: *"ONLY a true
StatusPass is a pass. Everything else — a contradicted FAIL and an unevaluable WARN
alike — is a non-pass that rolls the cutover back, because a transaction cannot
commit on evidence it does not have."*

The case that makes this bite is specific to updating, and **ADR-0001 predicted
it**: *"the log format drifts as the upstream image rebuilds on llama.cpp
master."* An image update is exactly when marker drift happens, so a new backend
image may be **perfectly good yet unprovable**. Villa rolls back and says:

> *"The new image could not be proven: residency markers not found. This image may
> be perfectly fine. Villa cannot show that it is, and will not commit a pin on
> evidence it does not have."*

**This makes marker drift a release-blocking defect.** A vetted pin that cannot be
proven on hardware must not ship — see [`RELEASING.md`](../RELEASING.md) §4.

### 5.4 Budgets and refusals

- **Per-subsystem budgets, no global cap.** A total cap would make failures depend
  on ordering, so the last subsystem gets blamed for time the first four spent.
- **A timeout is a Reject, not a Fail.** Both roll back; only the wording differs,
  and it matters — *"did not become healthy within 90s"* is a different claim from
  *"is broken"*, and only the first was observed.
- **A stopped stack is refused** for apply (`--check` still works, since it changes
  nothing). Starting services the operator deliberately stopped, proving against
  them, then stopping them again is a lot of unrequested state change — and if the
  restore-to-stopped step fails, `update` has left the stack running when it found
  it down.
- **`update` refuses; `doctor` diagnoses.** `update` does not grow diagnostics.

### 5.5 Retention and prune

One **known-good previous per subsystem**, recorded explicitly in `pinstate`, as a
**tuple** — digest + verbatim unit bytes + the config it was proven under — the
same capture `internal/backendswap` already performs. A bare digest is not
restorable weeks later when the unit renders differently.

**Prune is reference-counted across the whole store.** An image is removable only
when no current pin and no retained previous anywhere references it. This is a
safety property, not tidiness: `embedImage` and `vulkanImage` are the same digest
today, so a per-component prune could delete an image a **running backend depends
on** — not a lost rollback, a broken stack.

**A failed prune is a WARN, never a rollback.** The one place fail-soft is correct,
because the failure leaves *more* safety, not less.

Rationale and consequences: [ADR-0004](../adr/0004-villa-update-prunes-images-that-install-never-would.md).

## 6. Outbound

Two operations, two footprints, **stated separately** — one blended figure would be
true of villa's process and false of the operation.

| | **Check** | **Fetch** |
|---|---|---|
| Performed by | villa's own HTTP client | **Podman**, on villa's instruction |
| Shape | one HTTPS GET to the release endpoint | `podman pull`, gigabytes, several hosts |
| Bounded by | being one request | the **compiled-in allowlist** |

**Strictly on-command.** No timer, no opportunistic check inside other commands —
`status` is polled by the dashboard, so "opportunistic" would mean network access
on a UI refresh loop, which is telemetry-shaped even with an innocent payload.
Passive surfaces read the **last recorded** check and its age, never triggering a
live one.

This is what keeps **"zero telemetry" honest and unqualified**: a check the
operator invokes, carrying no body and no identifier, is not telemetry. If checks
ever become automatic, that claim must change with them.

**Silence over fingerprinting.** With no valid manifest, `--check` reports *"could
not check"* — a **Reject**, never *"nothing available"*. It does **not** fall back
to per-component registry calls, because the *subset* of images asked about leaks
which addons are enabled, and a fingerprint cannot be un-emitted. `--from-registries`
exists for when the user consciously chooses it, with the cost stated in its help.

Accepted cost: **villa will never tell you an update exists unless you ask**, and
if manifests lapse, `--check` goes quiet permanently. Both fail-closed, both real.

The honesty artifact is a **documented, unit-tested claim**, not a `verify update`
verb: the property is structural (compiled-in allowlist, on-command only), not
emergent from a policy that could drift, so it does not need `verify search`'s
netns/nft weight.

## 7. What was built

Everything below is written and gated. In dependency order, with where it lives:

| # | Piece | Where |
|---|---|---|

| 3 | **`pins.Table`** | `internal/pins` — accessors, not literals; `TestSeamGrepGate` passes with no allowlist entry |
| 4 | **the shared-digest drift test** | `internal/pins/drift_test.go` — over **vetted** pins only |
| 5 | **`pinstate` store** | `internal/pinstate` — with §4.3's two non-naive fallbacks, each tested explicitly |
| 6 | **the resolver** | `internal/pinresolve` — pure over an injected table + state |
| 7 | **the render-path migration** | the six sites; the backend via `inference.Repinned` inside the seam, the probe helpers untouched |
| 8 | **manifest schema + signer** | `internal/manifest`, `cmd/villa-manifest-sign` |
| 9 | **manifest verification** | `internal/manifestverify` — signature, serial, expiry, allowlist |
| 10 | **the check path** | `internal/updatecheck` + `internal/updatefetch` (one transport seam) |
| 11 | **the apply state machine** | `internal/updateflow` — pure core, `Deps`-injected |
| 12 | **prune** | `internal/prune` — reference-counted, one previous, WARN on failure |
| 13 | **`cmd/villa/update.go`** | cobra wiring, printing, exit codes, `live*Deps` |
| 14 | **the deferred unit tests** | both in `internal/updatefetch` |

### 7.1 Two migration hazards

**The `EmbedImage()` call sites are not all pins.** It has ~10 callers, and most
use it as a generic *"helper image that ships curl"* for probes (`verify_memory`,
`verify_search`, `verify_agent`, `doctor`, `status`, `install_searxng`). Those are
**not** the embedder's pin and must not become resolver calls — a probe helper does
not need an effective pin. The true render-path consumers are six sites where a pin
becomes a unit:

```
internal/orchestrate/memory.go:156    Image: qdrantImage
internal/orchestrate/memory.go:179    Image: embedImage
internal/orchestrate/openwebui.go:328 Image: openWebUIImage
internal/orchestrate/render.go:321    Image: image          (backend, via BackendFor)
internal/orchestrate/searxng.go:131   Image: searxngImage
internal/orchestrate/websafe.go:114   Image: websafeImage
```

A mechanical find-and-replace across `EmbedImage()` would be wrong.

**The shared digest needs a drift test, not a comment.** `memory.go` documents
`embedImage` as *"a DELIBERATELY INDEPENDENT const"* byte-identical to
`vulkanImage`, with a bare `// == vulkanImage` line. **Nothing enforces it.** Add a
cross-package drift test over the **vetted** pins only — effective pins are free to
diverge — cloning `TestEmbedGGUFFilenameSingleSource`. `TestSeamGrepGate` skips
`_test.go`, so the comparison trips nothing.

### 7.2 Seams

Follow the house pattern: the state machine is a pure core with every host effect
an injected `Deps` field, so the whole capture → mutate → prove → rollback flow is
driven from tests without a live host — as `internal/backendswap` already does, and
as the 93 existing `live*Deps` constructors in `cmd/villa` wire up.

## 8. The accepted costs

Collected here because each is a deliberate trade, and a reviewer meeting one in
isolation might try to "fix" it.

| Cost | Why it was accepted |
|---|---|
| Backend pins advance only for the **active** backend | proving the others needs four swaps; the landing spot must stay known-good |
| A **mixed** effective-pin state is a combination nobody vetted as a whole | failure isolation beats reverting four good updates; `doctor` surfaces it |
| Two vulkan-radv digests can coexist on disk | the alternative freezes the embedder or degrades the landing spot |
| Marker drift makes a good image **un-updatable** until a new villa ships | the alternative is committing on evidence villa does not have |
| The expensive proof runs **twice** per subsystem | the price of an honest rollback target and honest blame |
| One extra image per subsystem on disk | a digest can vanish upstream; recovery beats re-pulling something unavailable |
| Prune sometimes **no-ops** confusingly | reference counting is what stops it breaking a running stack |
| **`--check` goes quiet** if manifests lapse | fail-closed, and the alternative fingerprints the host |
| Villa **never tells you** unless you ask | a timer would put "zero telemetry" genuinely at risk |
| `update` reports a newer villa it **will not install** | self-replacement breaks the prove step and the websafe bind-mount |
| Adding a component **requires a villa release** | a new executable should require a signed binary, not a JSON file |
| Callers go through a **resolver**, not a constant | the cost of an effective pin existing at all |
| **Key custody** is a permanent obligation | the alternative lowers manifest trust to repo write access |

## 9. Open items for a human

1. **Generate and store the ed25519 keypair.** It must not touch a shared machine
   or CI. See [`RELEASING.md`](../RELEASING.md) § Key custody.
2. **Choose the `valid_until` window.** Months, not days — expiry silently ends
   update signalling for every install until publishing resumes.
3. **Decide the first manifest's serial**, and never reuse or regress it.
4. **Re-vet the compiled-in pins.** Eight of ten have drifted; that table is the
   floor on how stale a fresh install can be.
