# v1.11 spec: the workspace agent

A folder-scoped, sandboxed, strictly-local agent that does Cowork-class knowledge
work on the operator's own files: organise, reconcile, summarise, draft, in
Markdown, CSV and office formats. Assembled from the closed tickets on
[the v1.11 map](https://github.com/MatrixMagician/VillaStraylight/issues/156);
every claim here traces to the ticket that decided it, and every measured number
to the prototype or research note that produced it.

## 1. The problem

The stack answers questions. It does not do work on files. Anthropic's Cowork
gives an agent a folder and a task and the agent reorganises, reconciles and
drafts inside that folder, asking before it writes, inside a VM. Villa has every
part of that except the product: a capable local model, a coding agent with a
tool loop (`villa code`), rootless Podman, and a transactional house pattern. It
has no way to point the model at a folder and no boundary it could trust while
the model acts.

Measured on 2026-09-10 ([prototype](../prototype/cowork/RESULTS.md)): the local
model completed five Cowork-class tasks headlessly, four of them correctly, in
two to three and a half minutes each through a stand-in harness. Its one real
failure was **inventing facts under a "do not invent" instruction**. So the
product problem is grounding and the boundary, not model capability.

## 2. The shape of the answer

```
villa workspace add <folder>          register a folder as a workspace (the grant)
villa workspace list | remove <id>    the registered set; remove forgets, touches no file
villa work <workspace> "<instruction>"   submit a task and follow it; exits 0 / 1 / 2
villa work ... --detach               submit, print the task id, return
villa work ... --auto                 this task's writes need no approval (deletion still asks)
villa task list | show <id>           the task records, as a table or --json
villa task approve <id> [--all] | deny <id> | cancel <id>
villa tools-mode enter | exit         the chat unit served with the model's own template
villa install --workspace-agent       persists the gate, renders the network; the image is built separately
```

The **terminal verb is the spine**; the **dashboard** (view, approve, deny,
cancel) is a second phase in the same milestone; **Open WebUI is deferred**
([Surface](https://github.com/MatrixMagician/VillaStraylight/issues/157)).
`villa code` is untouched and shares no code path with `villa work`.

Exit codes reuse `doctor`'s vocabulary: `0` done, `2` done with flags that need
a look, `1` failed, refused, cancelled or interrupted. The `2` is the honesty
bit: a task whose document carries unsupported claims must not exit `0`.

## 3. The core model

### 3.1 A workspace is a registered grant

A **workspace** is a folder the operator has registered, persisted as a
`workspace` list in `config.toml`, the single source of truth. The sandbox's
one read-write mount renders from that list, never from an argument. `villa work`
on an unregistered path refuses with the remediation.

Registration is where fail-closed lives. `villa workspace add` refuses: a
relative path; a path `pathsafe` cannot resolve and contain (symlinks followed
once); the home directory itself, or a path outside it; a path containing villa's
XDG config or data roots; a workspace nested inside another (two grants over the
same bytes make "which task changed this file" unanswerable); a folder that does
not exist ([Surface](https://github.com/MatrixMagician/VillaStraylight/issues/157)).

### 3.2 A task is one-shot, and its record is a state machine

A **task** is one instruction run against one workspace, with a persisted
**task record** and a result. Follow-ups are a new task in the same workspace;
sessions are not in v1.11.

```
queued → running → awaiting_approval → running → done | flagged | failed | refused | cancelled | interrupted
```

`exit` is a pure function of `state`: `done` → 0, `flagged` → 2, every other
terminal state → 1. `flagged` is a state, not a field, so `villa task list` is
honest at a glance ([Task record](https://github.com/MatrixMagician/VillaStraylight/issues/170)).

- `refused` is villa declining before the sandbox started: an unregistered
  workspace, tools mode off, a VM that cannot start, a drifted Crush.
- `interrupted` is what recovery assigns, on dashboard-service start, to every
  record found non-terminal. A surviving sandbox is killed by name. Assigning it
  twice is a no-op, and recovery never re-queues: re-running a task is the
  operator's command.

The record is one `jsonstore` document per task under the XDG data root,
`tasks/<id>.json`, `schema: 1`, append-only after submission:

| Field | Content |
|---|---|
| `id` | time-ordered with a short random suffix, `20260910-120115-4f2a`; the sandbox container is `villa-task-<id>` |
| `workspace`, `instruction`, `mode` | the grant, the prose, `ask` or `auto` |
| `state`, `exit` | as above |
| `submitted_at`, `started_at`, `finished_at` | RFC 3339 UTC |
| `harness` | `crush` and the version the bridge asserted |
| `files` | `[{path, action: created | modified}]` from the harness's file events |
| `approvals` | `[{seq, tool, action, path, asked_at, answer, answered_at, by}]`, `answer` ∈ `allow | allow_session | deny`, `by` ∈ `prompt | dashboard | cli` |
| `grounding` | `{checked, documents: [{path, claims, unsupported: [{claim, reason}]}]}` |

A sibling `tasks/<id>.log` of JSON lines carries villa's narration events **and**
every harness message event. Crush's own SQLite lives on the sandbox tmpfs and
dies with the VM, so the log is the only transcript that survives; the terminal
prints narration only and `--verbose` replays the log. Records are kept forever:
no automatic deletion and no removal verb in v1.11.

`villa task show --json` emits the record verbatim; `villa task list --json`
emits `{schema, tasks: [{id, workspace, state, submitted_at, finished_at, exit}]}`.
Both are byte-frozen by goldens and evolve append-only with a schema bump.

### 3.3 An approval is a class, answered by a table

An **approval** is a task's request to perform a write-class action, answered by
the operator. The **classifier is the harness's tool layer**: every Crush tool
call arrives as a permission request carrying an `Action` ∈
`read | write | execute | list | fetch | download`, a path and typed params.
Villa never re-derives the class; a pure `internal/approval` table decides from
it ([Approvals](https://github.com/MatrixMagician/VillaStraylight/issues/159)).

Two modes, not Cowork's three:

| Mode | `read` / `list` | `write` | `execute` |
|---|---|---|---|
| `ask` (default) | auto | ask | ask |
| `auto` (`--auto`, per task, never a config default) | auto | auto | auto only for Crush's safe-command list and a villa-rendered allowlist (`python3`, `soffice`, `mv`, `cp` under the workspace); else ask |

**Deletion always asks**, in every mode. Crush has no delete tool, so deletion is
a bash `execute` matching a conservative pattern (`rm`, `rmdir`, `unlink`,
`shred`, `trash`, `git clean`, `find … -delete`). The docs say this is a pattern,
not a proof, the way `websafe` says it flags and never claims safe. Cowork's Skip
is dropped: it is Crush's `permissions/skip`, which also skips the deletion rule,
so the two claims cannot coexist.

Attached, an approval is answered at the prompt: `y` once, `N` deny (default),
`a` for the rest of this task (Crush's `allow_session`). Detached, the task parks
in `awaiting_approval`, with no timeout, until `villa task approve <id> [--all]`,
`deny`, the dashboard, or `cancel`. A denial is fed back to the model, recorded
and narrated, and does not change the exit code: `2` is for flags the operator
has not seen, and a denial is one they issued.

`fetch`, `web_fetch`, `web_search`, `sourcegraph` and `download` are rendered
into Crush's `disabled_tools` for workspace tasks. The internal network is the
boundary; the render is the courtesy.

### 3.4 The sandbox is a microVM per task

A **sandbox** is a libkrun microVM (`podman --runtime=krun`) with one workspace
mounted read-write. The prototype settled that the same image, volume grant and
network run under krun unchanged, with a separate guest kernel and a 0.5 s
start ([prototype addendum](../prototype/cowork/RESULTS.md)).

**Why per task, not a long-lived unit.** Measured on the box
([Sandbox unit](https://github.com/MatrixMagician/VillaStraylight/issues/161)):
under krun, `podman exec` is unsupported, unix sockets on a bind mount fail in
both directions, and a port published from a container on an `--internal`
network is unreachable from the host under crun and krun alike. **The container's
stdio and files on the mount are the only channels across the boundary.** A
per-task VM's stdio is its channel, cancel is `podman kill`, memory returns
between tasks, and nothing leaks from one task into the next.

The launch is a pure render, fixed args, never a shell:
`orchestrate.RenderSandboxRun(cfg, workspace, task) []string` emits
`--runtime=krun`, `--rm`, `--init`, `--network villa-sandbox`, `--read-only`,
`--tmpfs /tmp`, `--volume <workspace>:/workspace:Z`, the `villa` binary
bind-mounted read-only (the websafe unit's pattern; the CGO-free build gate stays
load-bearing), `--memory` and `--cpus` from config (defaults 8g and 4; the
prototype ran at 4g, and LibreOffice with Java recalc argues for more), no
`/dev/dri`, no `/dev/kfd`, no models volume. Crush's data directory points at the
tmpfs, not the grant (the prototype found `.crush/` in the workspace otherwise).

The long-lived units are `villa-sandbox.network` with `Internal=true` (the
`villa` network has egress; a task on an internal network reached llama and
nothing else) and a second `Network=villa-sandbox` line on the inference unit.
Both render from config and are frozen by goldens.

**Root in the VM is the boundary.** krun ignores `--user`; the guest runs as
uid 0 and host files come out owned by the operator. Documented, not discovered.

**When the VM cannot start, the task is refused** with doctor's finding as the
remediation. Cowork degrades to file tools outside the VM; villa has no file
tools outside the VM and must never run the agent unsandboxed, so there is
nothing honest to degrade to.

### 3.5 Tools mode is a flag on the chat unit

Tool calls over llama-server need `--jinja`, which today only coding mode
renders, and coding mode is a model swap. **Tools mode** is the chat unit served
with the model's own chat template, without the swap
([Tools mode](https://github.com/MatrixMagician/VillaStraylight/issues/160)):

- one `tools_mode bool` config field, `omitempty`, so every existing unit renders
  byte-identical;
- one gate, `subsystem.ToolsOn(cfg) = tools_mode || coding_mode`, answered once;
  coding mode implies tools mode, so no second boolean has to stay in sync;
- `--jinja` emitted from one place in the inference seam (`RunSpec.Tools`;
  `CodingModeSpec` sets it and keeps the sampling and cache-reuse lines);
- the context floor from the catalog entry's `agent_ctx`, served as
  `max(cfg.ctx, agent_ctx)`, refused with the fit remediation when it does not
  fit. The prototype's 64k came from a 47k stand-in overhead; Crush's whole
  two-turn smoke exchange cost 9.5k prompt tokens, so the floor is a catalog
  fact to measure, not this note's number;
- `villa tools-mode enter | exit` clones `speculation set`'s transactional shape
  (capture → save → re-render → restart → prove → rollback), proven by the
  residency proof plus the tool-call edit probe `install --coding-agent` already
  runs; `villa install --workspace-agent` persists the gate;
- `villa work` on a tools-mode-off stack refuses with that remediation, the way
  `villa code --agent claude` refuses without coding mode. It never flips the
  stack itself, so one command cannot observe two answers.

`status` shows `mode: tools`; `doctor` gains a drift check (the served unit
carries `--jinja` iff `ToolsOn`). Whether `--jinja` changes what Open WebUI users
see is an on-hardware proof item for the build, not an assumption.

## 4. The harness

**Crush v0.76.0, villa's pinned coding agent, runs inside the sandbox as
`crush server`; villa's own runner drives it and owns approvals, narration,
cancel and the grounding audit**
([Harness](https://github.com/MatrixMagician/VillaStraylight/issues/158)).

What the source at tag `v0.76.0` settled:

- `crush run` (non-interactive) calls `AutoApproveSession`; it is yolo by
  construction and can never carry `ask` mode.
- `crush server` exposes the loop over HTTP: workspaces keyed by cwd, a prompt
  endpoint, an SSE stream (`permission_request`, `permission_notification`,
  `message`, `file`, `agent_event`, `run_complete`), a grant endpoint taking
  `allow | allow_session | deny`, cancel, and a file tracker listing what a
  session read. The Crush TUI is a client of the same surface.
- `crush.json` is already villa-rendered (`internal/agent/render.go`), so
  disabling tools and pointing the provider at the internal-network server is a
  render, not a patch.

Two new nouns. The **bridge** is the in-sandbox `villa` process that starts
`crush server` on a guest-local socket and relays its events and grants as JSON
lines over the container's stdio. The **runner** is villa's host-side driver of
one task: it launches the sandbox, submits the instruction, answers each
permission request from the approval table or the operator, writes the record
and the log, narrates, cancels, and runs the audit after `run_complete`. The
bridge asserts Crush's `GET /v1/version` against the pin at start, so a drifted
binary refuses before a task runs.

**Measured** ([chosen-harness prototype](https://github.com/MatrixMagician/VillaStraylight/issues/166)):
Crush inside the sandbox reached parity or better on four of the five tasks and
was three to six times faster than the stand-in on all five (77, 55, 55, 22 and
50 seconds against 171, 208, 156, 125 and 137). It invented nothing on the memo.
Its one regression, a wrong totals row in the reconciliation, the audit caught.

The villa-owned Go loop over a villa tool server stays the documented fallback,
to be taken up only if the build finds Crush's coding-shaped prompt fighting
document work; the prototype did not.

## 5. The task lifecycle

1. **Submit.** `villa work` posts to the dashboard service's loopback API and
   follows the task over SSE; `--detach` prints the id. The runner lives in
   `villa-dashboard.service` ([Posture](https://github.com/MatrixMagician/VillaStraylight/issues/163)):
   it is already the long-lived villa process, the dashboard phase needs the task
   state in-process, and a separate unit would need an approve/deny IPC between
   two villa processes. When the service is down, `villa work` refuses with the
   remediation.
2. **Refuse or queue.** Unregistered workspace, tools mode off, VM unavailable
   (doctor's finding), drifted Crush → `refused`, before anything starts.
   Otherwise `queued`. **One task runs at a time, globally**: one model, one
   sandbox image, one llama-server; parallel tasks would only contend for the
   same tokens per second.
3. **Run.** The runner renders and launches the sandbox, the bridge starts Crush,
   the instruction goes in with the citation requirement (§6). Every permission
   request is decided by the table or parked for the operator. File events and
   messages append to the log; narration streams to the terminal and the
   dashboard.
4. **Audit.** After `run_complete`, one model call per file the task created or
   modified (§6). Any unsupported claim, or an audit that could not run →
   `flagged`.
5. **Finish.** The record's terminal state is written, the sandbox exits
   (`--rm`), the terminal prints the summary and exits with the record's code.

`villa task cancel <id>` drops a queued task or kills a running one by name and
marks `cancelled`; the workspace keeps what was written. Undoing partial work is
a new task, not villa's guess.

Routes: `GET /api/tasks`, `POST /api/tasks`, `GET /api/tasks/{id}`,
`GET /api/tasks/{id}/events`, `POST /api/tasks/{id}/approve | deny | cancel`.
The server stays loopback-only; nothing here widens the bind.

## 6. Grounding

Two layers ([Grounding](https://github.com/MatrixMagician/VillaStraylight/issues/162)).
The **instruction** requires every produced document to cite the workspace file
each factual claim comes from. The **audit** is a villa-run second pass after
`run_complete`: for each file the task created or modified, one chat completion
against the chat unit over loopback, the sources being the files the session
read (the harness's file tracker), listing every claim and either the supporting
passage or `UNSUPPORTED`. The document is left as written; villa flags, it does
not edit.

**Measured** on the prototype's outputs, `temperature 0`, one call per document:

| Document | Claims | Unsupported | Wall |
|---|--:|--:|--:|
| the stand-in's memo that invented facts | 19 | 12, every named invention among them | 13 s |
| Crush's memo | 12 | 0 | 13 s |
| Crush's reconciliation (wrong totals row) | 23 | 4: the total paid with the right figure computed, the outstanding derived from it, and two strict readings | 42 s |
| Crush's action items (correct) | 17 | 1, arguable | 25 s |

> **Footnote from the build.** The same audit outputs, parsed by
> `internal/grounding`, count 10 of 19 unsupported for the invented memo and 5 of
> 23 for the reconciliation, not the 12 and 4 above. The 12 and 4 were the
> model's own TOTAL lines, which were wrong in both directions; villa's parser
> counts each claim's marker and ignores the summary line. The other two rows
> were not re-counted.

So the audit catches inventions and arithmetic slips at under a minute per
document, with a strict-reading cost of one to three flags on a correct
document. Exit `2` on any flag is the right default; a flag is short and a human
clears it in seconds.

Two rules the build must carry. **The audit call disables thinking**
(`enable_thinking: false`): with it on, the model spent its whole 4096-token
budget reasoning and returned no content. **A clean audit is "the auditor found
none", never "grounded"**: the auditor is the same model that wrote the
document, and the docs say so the way `websafe`'s do.

## 7. Office formats

The sandbox image is villa-built from a Containerfile in the tree:
`fedora:44` + `python-docx` + `openpyxl` + poppler + `libreoffice-writer` and
`-calc`, 1.54 GB
([research](../research/office-formats.md)). It gets a row in `pins.Table`
carrying the built digest and a `Sandbox` subsystem in `internal/subsystem`
(owns no persistent state), so it rides `villa update` like every other image;
the rebuild-versus-bump ambiguity is reported the way the ROCm image's is.

Python drives the libraries; LibreOffice is only the renderer and the recalc
engine, never the author. An xlsx write is **write → recalc → prove**, because
openpyxl stores no cached formula values.

**Measured** ([xlsx prototype](https://github.com/MatrixMagician/VillaStraylight/issues/169)):
the model authored a structurally correct workbook on its first attempt, then
wrote its own UNO recalculation that spawned `soffice` as a background listener
and waited on it until the 1200 s timeout. The research's one-line
`soffice --convert-to xlsx` recalc, run afterwards under krun with no network,
took 3 s and rendered the PDF in the same run. And the read-back would have
failed the task honestly: its `SUMIF` never matched the bank export's
hyphen-less or reference-less descriptions, so every paid cell recalculated to
zero.

Three rules follow. **Recalc and render are villa-shipped scripts the model
invokes, never code it writes.** **The read-back is part of an xlsx task's
proof, not a courtesy**: the task is not done until the recalculated values were
read and compared. **The image ships `which`** (the model coped without it).

## 8. Posture

Three claims, separated ([Posture](https://github.com/MatrixMagician/VillaStraylight/issues/163)):

- **Zero telemetry**: untouched. A task sends nothing off the box; the sandbox
  has no egress; the runner talks to loopback.
- **Outbound strictly on-command**: untouched, because a task has no outbound at
  all. On-command is a claim about outbound, not about compute.
- **"never on a timer and never in the background"** (README line 3): the letter
  breaks the moment a detached task exists. The sentence is rescoped to outbound
  in one qualified place, the way the v1.8 ticket qualified "strictly local"
  while keeping "zero telemetry" whole, and `docs_gate_test.go` gains a second
  claim pattern beside `updateOutboundClaim` so an unqualified background or
  timer claim fails the build.

**Villa-owned timers are deferred to v1.12.** A timer is the first thing villa
would do without a command; it deserves its own posture ticket with the docs
gate written first. The queue and `--detach` ship now, and the docs note in one
line that an operator may drive `villa work --detach` from their own systemd
timer.

**Browser use is deferred to v1.12**
([Browser use](https://github.com/MatrixMagician/VillaStraylight/issues/168)).
The egress proxy does not exist yet, and shipping a browser in the milestone
that introduces "a task has no egress" would make that claim born qualified. The
shape is recorded so nothing here forecloses it: a sibling `villa-browser` krun
unit on the internal network running Playwright MCP headless with `--no-zygote`,
egress only through an allow-listing `villa-egress` proxy, reached by Crush as an
`http` MCP server, with per-origin grants as one more row-set in
`internal/approval`.

## 9. The dashboard phase

Ships in the same milestone, after the terminal spine: workspaces, the task
list, a task's record and narration, and approve / deny / cancel. It reads the
same store and the same SSE stream the terminal does. Submitting a task from the
dashboard is deferred with the chat surface: it adds an input surface the
loopback-only server does not have today.

## 12. The accepted costs

| Cost | Why it was accepted |
|---|---|
| A third-party binary in the task path | Crush is already pinned, checksum-verified and drift-detected; a villa-owned loop is months of harness work before the first task |
| Crush's API is unversioned beyond `GET /v1/version` | the bridge asserts the pin at start, and a pin bump re-proves the bridge in the on-hardware suite |
| A VM per task, started fresh every time | 0.5 s; the alternative needs a channel that does not exist under krun |
| Root inside the VM | krun ignores `--user`; the VM is the boundary, and the fact is documented rather than discovered |
| The dashboard service now does work, not only reads | the alternative is an approve/deny IPC between two villa processes |
| One task at a time | one model and one llama-server; parallelism would only share tokens per second and make "which task changed this file" hard |
| The deletion rule is a pattern, not a proof | Crush has no delete tool; the pattern is stated as such, and the grant bounds what it can reach |
| `auto` mode rests on an allowlist | there is no per-action classifier for bash beyond Crush's safe list; the docs say so |
| One to three strict audit flags on a correct document | the alternative is a memo that invents facts and exits 0 |
| The auditor is the model being audited | a clean audit is evidence, not proof, and is reported as such |
| 1.54 GB of sandbox image, mostly LibreOffice | a 434 MB image ships files the agent cannot look at |
| Task records and logs are never deleted | deletion lives in exactly two named places today; a third needs its own reason |
| The README sentence gets a qualification | the alternative is a false sentence guarded by nothing |
| Timers and browser use wait for v1.12 | both would qualify a claim in the milestone that makes it |

## 13. Open items for a human

1. **The tools-mode context floor.** Measure Crush's real overhead on the chat
   entry and write `agent_ctx` for it in the catalog; do not carry 64k forward.
2. **Whether `--jinja` changes Open WebUI's chat.** Answered by the build: on
   this pin (llama.cpp b9536, Qwen3.6-35B-A3B) the chat template, the tool-call
   output and plain replies are byte-identical with and without it, so
   `GETTING-STARTED.md` carries no note. The flag stays load-bearing as the
   declaration `doctor TMD-01` and `villa work` key on.
3. **The audit prompt's strictness.** The measured flags on correct documents were
   period labels and generation dates. Decide whether the prompt excludes
   document metadata, or whether exit `2` on those is the honest default.
4. **The `--memory` default.** 8g is a guess above the prototype's 4g; measure a
   LibreOffice recalc under krun before freezing it.
5. **A name for `TLS-01`** that does not read as TLS. Answered: `TMD-01
   tools-mode drift` (doctor `--json` schema 8).
